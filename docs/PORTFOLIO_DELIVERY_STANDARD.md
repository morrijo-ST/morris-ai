# Portfolio Delivery Standard

Every public portfolio repo should feel like a small consulting engagement, not a coding exercise.

## Required buyer-facing assets

### README.md
Must answer in the first screen:
- What business problem does this solve?
- What does the system do?
- What is the architecture?
- What can the buyer try right now?
- What technologies are demonstrated?

### Case Study
Use the structure:
1. Business problem
2. Existing/manual process
3. Risks and bottlenecks
4. Requirements
5. Architecture
6. Implementation
7. Controls
8. Results on synthetic demonstration data
9. Production considerations
10. Future enhancements

### Architecture
Include:
- source systems
- ingestion path
- canonical data layer
- business-rule layer
- orchestration
- AI layer where appropriate
- application/reporting layer
- logging / retries
- approval / human-in-loop path

### Business Rules
Rules must have IDs and deterministic descriptions, for example:

`BR-001 — An exact invoice reference + exact amount may auto-match unless an approval threshold is triggered.`

### Data Dictionary
Document public synthetic entities and fields. Never copy confidential production schemas verbatim.

### Security
Describe:
- secrets management
- least privilege
- PII/financial-data considerations
- AI guardrails
- audit logging
- separation between deterministic calculations and AI recommendations

### Runbook
Describe:
- startup
- health checks
- common failures
- retry behavior
- manual override
- monitoring
- recovery

## Required proof assets

Every finished portfolio project should eventually contain:

1. **Cover image** — clear business outcome, not a collage of tools.
2. **Problem / solution image** — manual state → automated state.
3. **Architecture diagram** — readable by a technical buyer.
4. **Working-product screenshot** — dashboard / workflow / application.
5. **Control / exception screenshot** — proves production thinking.
6. **Impact / KPI image** — label synthetic/demo outcomes clearly.
7. **60–120 second demo video** — show the system rather than narrating slides.

## Code quality standard

Public demos should include where applicable:
- deterministic synthetic data generator
- seed for reproducibility
- separated business logic and UI
- requirements / dependency file
- `.gitignore`
- `.env.example` if secrets would be used in production
- automated tests
- descriptive commit history
- no production credentials
- no employer names or internal IDs

## Public demo standard

A live demo should:
- load without credentials
- explain that data is synthetic
- surface the business KPIs immediately
- include filters / interaction
- contain at least one workflow or decision path
- demonstrate exceptions / controls, not only happy-path charts
- not require a prospect to read code to understand value

## Upwork adaptation

For each repo create:

### Portfolio title
Business outcome + system type.

### 1-sentence hook
What manual / expensive process this replaces.

### Challenge
2–4 sentences.

### Solution
3–6 bullets.

### Technical architecture
Short enough for a business buyer, specific enough for a technical buyer.

### Demonstration outcome
Only report metrics generated by the demo or real metrics you are authorized to disclose. Clearly label synthetic results.

### Call to action
Describe the types of client environments the pattern can be adapted to.

## Principle

The portfolio should communicate:

> I can discover the business process, architect the system, build the data layer, implement the automation, design controls, create decision-ready reporting, document it, and hand it over.
